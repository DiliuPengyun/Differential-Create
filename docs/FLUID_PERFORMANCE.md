# 微分动力：流体网络性能测试

测试使用当前的[虚拟空气与有序流体模型](FLUIDS.md)。行为划分见[覆盖矩阵](FLUID_COVERAGE.md)，性能入口为 [FluidNetworkPerformanceTests](../src/gameTest/java/com/diliupengyun/differential_create/tests/FluidNetworkPerformanceTests.java)。

## 运行入口

```powershell
.\gradlew.bat runFluidBenchmarkServer
.\gradlew.bat runFluidBenchmarkServer -PfluidPerfCase=loops
```

Linux 使用 `./gradlew`。每次运行在 `build/fluid-network-performance/runs/` 中创建独立测试世界，结果写入控制台与该世界的 `logs/latest.log`。普通游戏回归不运行性能场景。

| `fluidPerfCase` | 管道与泵总数 | 场景 |
| --- | --- | --- |
| `straight` | 64 / 256 / 1024 | 满液直管，两端原生储罐，1 泵实际输送 |
| `branches` | 65 / 257 / 1025 | 16 / 64 / 256 个侧支路，高水位储罐供液 |
| `loops` | 65 / 280 / 1045 | 满液网格闭环，4 / 16 / 64 泵 |
| `slugs` | 65 / 280 / 1045 | 同样网格中的零散液段与空气 |
| `idle` | 64 / 256 / 1024 | 稳定全空气管网，无驱动及运动 |
| `mixed` | 65 / 280 / 1045 | 水、空气、熔岩的有序队列闭环 |
| `endurance` | 65 | 4 泵三相闭环，预热 1200 次后测量 |
| `mutation` | 65 / 1045 | 4 / 64 泵满液网，每次采样关闭或重开连接 |

默认 `all` 执行 21 组。数量计入替换直管的泵，不计储罐、电机与齿轮。

## 测量口径

场景先等待所需区块进入 ticking 状态，随后填充初始库存。普通场景预热 24 次，长期场景预热 1200 次；随后计时 96 次 `MachiningClock.advance` 调用，每次请求推进一个游戏 tick。测量包含流体压力更新、原生库存提交、泵反作用、机械积分及状态发布。`mutation` 还包含实际关面、重开、邻居更新与重新捕获。区块就绪等待不计入耗时。

计时期间保留连续演化的状态。含泵场景须有新接受的泵流量；零散液段和混合场景须改变实际队列。检查各真实身份及空气守恒、满容量、有限速度和队列段数，避免用冻结库存或旧保存流速通过验收。

输出中位数、P95、均值、最大值、捕获耗时，以及更新次数、压力处理、重试和最短时间步。客户端更新标签与 NBT 编码另行计时；全量标签快照不等于实际每 tick 的发送量。

非 `mutation` 场景另输出 `FLUID_NETWORK_STEPS`：`transport` 是实际库存搬移次数，`pressure_solves` 是压力求解次数，`completed_fraction` 是已提交流体时间与请求流体时间之比。这个比例按活动连通分量的时间求和，不按管道数量加权；稳定休眠场景没有待完成的流体工作，记为 1。时钟调用完成不代表全部流体时间已提交；触及工作预算时必须同时报告这个比例，不能把少推进时间误判为加速。

## 取消流量硬上限后的复测（2026-10-24）

原来的统一缩放会把普通 100 mB 管段的流量压到不超过 50 mB/tick；缩小时间步也不能绕过这一上限。当前改为按实际流量选择库存搬移的时间步，不改写物理流量。低流量通常仍只更新一次。没有外部端口、每个管段装满同一种完整流体身份的闭环，库存搬移是恒等操作，因此只更新真实压力和动量；混合身份、空气界面及外部端口仍执行实际库存搬移。

本次将修复前的两个生产类放入隔离构建，使用相同的当前测试场景及完成比例统计，与新实现分别运行完整 21 组。下列为单轮代表性记录，耗时单位 ms／时钟调用；旧版仍有错误的限流，因此比较不代表两者完成了相同的输送工作：

| 场景 | 旧版中位 | 新版中位 | 旧版流体时间完成率 | 新版流体时间完成率 |
| --- | ---: | ---: | ---: | ---: |
| 64 直管、1 泵 | 1.230 | 1.233 | 100% | 100% |
| 65 满液闭环、4 泵 | 1.565 | 0.725 | 100% | 100% |
| 280 满液闭环、16 泵 | 2.013 | 2.647 | 100% | 100% |
| 1045 满液闭环、64 泵 | 6.621 | 9.743 | 98.96% | 100% |
| 65 三相闭环、4 泵 | 0.582 | 1.055 | 100% | 100% |
| 280 三相闭环、16 泵 | 3.173 | 3.561 | 100% | 98.94% |
| 1045 三相闭环、64 泵 | 10.413 | 9.374 | 56.25% | 42.57% |

三个满液闭环的新版均只进行了 96 次压力求解，没有 FIFO 库存搬移。65 管段三相闭环进行了 180 次搬移、185 次压力求解，完成全部请求时间；其最大流量约 243 mB/tick，而旧版被限制在 50。1045 管段三相大网的新旧版本都受到既有 4 ms 软预算约束；新版的中位耗时虽然较小，实际完成比例更低，属于仍需优化的性能边界，不能解释为性能提升。

21 组均通过有限性、逐身份守恒及实际库存演化检查，不表示它们都能在预算内完成全部模拟。单轮 JVM 热身、机器负载与非线性求解路径影响明显，不据此承诺固定百分比的提速或降速。原始本地记录为 `build/flow-limit-fix/baseline-final.log` 与 `build/flow-limit-fix/optimized-performance.log`，不随仓库分发。

独立的高流量回归还验证了无外力环流不被限速损耗、不同数值时间步及管内容量不改变稳态解、分叉连续性和每个子步的库存安全；原生水与熔岩场景均实际输送到储罐，而非仅显示较高流速。这些测试位于专用测试源集，正式包不包含它们。

## 历史基准（2026-10-08）

2026-10-08 提交前复测通过 21 组独立基准，当时的本地原始记录位于 `build/cleanup-verification/verification.log`，不随仓库分发。各组接受 96 次更新，重试为零，最短时间步为一个游戏 tick。以下单位为 ms／完整物理更新；这些数据只对应当时版本，当前性能应重新执行上面的基准确认：

| 场景 | 中位 | P95 | 最大 |
| --- | ---: | ---: | ---: |
| 1024 直管、1 泵 | 1.614 | 2.087 | 2.739 |
| 1025 分叉管段 | 2.764 | 3.703 | 5.292 |
| 1045 满液闭环、64 泵 | 4.634 | 5.579 | 5.928 |
| 1045 部分灌注闭环 | 1.692 | 2.505 | 7.232 |
| 1024 稳定全空气管段 | 0.271 | 0.371 | 0.629 |
| 1045 三相闭环、64 泵 | 6.206 | 8.878 | 12.002 |
| 65 三相闭环、4 泵，长期预热 | 0.376 | 0.502 | 0.620 |
| 65 满液管段、4 泵，连续改连接 | 0.368 | 0.890 | 1.508 |
| 1045 满液管段、64 泵，连续改连接 | 4.822 | 7.901 | 9.546 |

三相大网最多 64360 段，长期小网最多 5889 段，均通过段数与逐身份守恒检查。三相大网的全量客户端标签为 2055221 字节，编码耗时 12.087 ms；这项耗时单独报告。

计时排除搭建、预热、拆除、完整世界 tick、网络传输与客户端绘制。每世界 4 ms 是可推迟流体工作的软预算，完整物理更新仍可能超过它。不同 JVM 的热身与调度会影响结果；这些数据不能直接作为服务器整体 MSPT、固定加速比例或任意工厂恒定 20 TPS 的保证。
