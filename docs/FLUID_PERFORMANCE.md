# 微分动力：流体网络性能测试

## 测量方法

测试入口为 `./gradlew runFluidBenchmarkServer`（Windows：`.\gradlew.bat runFluidBenchmarkServer`）。测试专用命名空间为 `differentialcreate_perf`，普通游戏回归不会运行性能场景。每次调用在已忽略的 `build/` 中创建一个全新世界，不复用上次失败后留下的管网；捕获后校验参与物理时钟的管道数量与当前场景一致。测试完成或失败时均拆除该场景。

每个场景等待原版连接行为完成初始化后，用正式 `MachiningClock.advance` 预热 24 个物理 tick，再计时 96 个 tick。每次调用完整推进 50 ms 的模拟时间，包含管内库存与前沿事件、共同压力求解、泵与机械轴传能、原版库存存取以及物理状态发布。计时不包含世界生成、方块放置、预热、拆除、原版全部方块实体 tick 或客户端渲染，所以结果是服务器物理部分耗时，不能直接当作完整服务器 MSPT 或客户端帧率。

计时期间场景持续演化，不在每次采样前恢复冻结快照。检查原版储罐、管内液体和管口小数余量的总量守恒、所有速度有限，以及满的闭环没有凭空产生空隙。输出中位数、P95、均值、最大值及首次管网捕获耗时；捕获时间不包含放置和世界加载。另记录已接受的共同时间步、联立迭代次数、重试次数与最短时间步，区别正常前沿事件和求解停滞。

| 场景 | 管道与泵方块总数 | 泵数 | 运动条件 |
| --- | --- | --- | --- |
| 长直管 | 64 / 256 / 1024 | 1 | 灌满管路，两端原版储罐，泵推动实际输送 |
| 多分支 | 65 / 257 / 1025 | 0 | 16 / 64 / 256 个侧支路，由高水位原版储罐供水 |
| 网格回路 | 65 / 280 / 1045 | 4 / 16 / 64 | 灌满的 5×5 / 10×10 / 19×19 网格，多泵共同驱动 |
| 零散水团 | 65 / 280 / 1045 | 0 | 同样的网格，水平运动水团、其余管段为空 |

数字计入替换直管的动力泵，未计储罐、创造马达与齿轮。每类可通过 `-PfluidPerfCase=straight|branches|loops|slugs` 单独运行。测试代码见 [FluidNetworkPerformanceTests](../src/main/java/com/diliupengyun/differential_create/tests/FluidNetworkPerformanceTests.java)。

## 对照范围

改动前的对照为提交 `7f2eb85` 的正式 `FluidKinetics`、`IdealFluidSolver`、`ReducedFluidGraph`、`PipeFilling` 和 `PipeContents`。对照和新版使用同一性能场景与其他正式代码，分别编译到独立目录、启动独立 JVM。对照仅补上相同的管道计数与迭代计数接口，没有更改物理代码。复杂空管中的分流轨迹已经改变，因此两版在相同初始条件下演化后的运动不同；结果表示这些实际场景的成本，不能当作每次压力矩阵计算都增加同样百分比。

本次机器为 Windows、AMD Ryzen 5 9600X（6 核 12 线程）、JDK 21、Minecraft 1.21.1 / NeoForge 21.1.238。数据只代表此机器上的受控物理场景。大型工厂的其他设备、区块卸载、第三方接口与客户端渲染需要另测。

## 2026-10-03 实测结果

正式实现的 12 个场景全部完成。全场景最大水量误差约为 5.9 × 10⁻¹¹ mB；全部速度有限，满闭环没有凭空出现空段。以下是一次独立 JVM 运行的结果，每行计时 96 个物理 tick，不是重复运行的统计置信区间。

| 场景 | 管道与泵方块总数 | 泵数 | 中位 ms | P95 ms | 最大 ms | 首次捕获 ms |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 长直管 | 64 | 1 | 2.190 | 3.341 | 21.514 | 3.549 |
| 长直管 | 256 | 1 | 3.848 | 5.954 | 20.421 | 1.039 |
| 长直管 | 1024 | 1 | 6.866 | 11.811 | 18.601 | 2.019 |
| 多分支 | 65 | 0 | 1.338 | 1.902 | 8.921 | 0.517 |
| 多分支 | 257 | 0 | 2.635 | 3.062 | 22.616 | 0.679 |
| 多分支 | 1025 | 0 | 11.269 | 17.035 | 71.260 | 2.728 |
| 多泵回路 | 65 | 4 | 2.353 | 7.929 | 8.528 | 0.177 |
| 多泵回路 | 280 | 16 | 26.066 | 39.240 | 46.155 | 0.633 |
| 多泵回路 | 1045 | 64 | 231.512 | 261.601 | 556.081 | 2.864 |
| 零散水团 | 65 | 0 | 1.243 | 2.798 | 13.374 | 0.170 |
| 零散水团 | 280 | 0 | 4.263 | 38.604 | 61.382 | 0.509 |
| 零散水团 | 1045 | 0 | 15.946 | 138.964 | 290.535 | 1.815 |

20 TPS 对应整个服务器 tick 的 50 ms 预算。长管和树状分支在本机上的通常成本较低；280 个管道与泵、16 个泵的网格已经消耗约半个总预算，其 P95 约 39 ms，还要给其他设备与世界 tick 留出时间。1045 个管道与泵、64 个泵的网格中位耗时约 232 ms，不能维持 20 TPS。1045 管道的零散水团中位约 16 ms，但 P95 约 139 ms，最大约 291 ms，会出现明显峰值。因此不能承诺任意复杂管网的性能影响有限，也不能仅按管道数量估算成本。

上述大网格多泵场景在 96 tick 内接受 1372 个共同时间步，完成 27161 次联立迭代、1153 次重试；零散水团大网格为 1194 个时间步、11934 次迭代、1088 次重试。压力回路、泵轴耦合和真实前沿事件共同决定成本，下一步优化重点是减少重复联立工作，而不是增加阻力、删除薄水段或限制流速。

实现过程中已修正满管重复触发虚假前沿事件、零入流满接头产生空隙，以及干燥间隙把空空间输入湿接头的问题。最终十二个场景没有发生事件不收敛或液体碎段失控；此前失败或复用旧世界的测量不列入本表。仍需另测更长时间的大型工厂、自然卸载重载和完整客户端玩法。

## 改动前对照

旧版在 1025 管道、256 个侧支路场景中报告 `Fluid flow correction did not converge`，没有形成有效计时结果；该问题由新版树状压力消元与局部连续性检查覆盖。已经完成的相同场景对照如下，单位也是 ms／物理 tick：

| 场景 | 方块数 | 旧版中位 / P95 | 新版中位 / P95 |
| --- | ---: | ---: | ---: |
| 长直管 | 64 | 2.060 / 2.777 | 2.190 / 3.341 |
| 长直管 | 256 | 4.200 / 5.468 | 3.848 / 5.954 |
| 长直管 | 1024 | 7.990 / 11.534 | 6.866 / 11.811 |
| 多分支 | 65 | 1.160 / 1.776 | 1.338 / 1.902 |
| 多分支 | 257 | 3.805 / 4.218 | 2.635 / 3.062 |

这些单次运行存在 JIT、垃圾回收和调度波动；部分指标变快、部分变慢，不据此宣称固定比例的性能改善。旧版未完成的复杂场景不能用零耗时填充或计算百分比。
